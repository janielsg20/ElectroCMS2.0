# M08.1 — Content Type y Field Registry

**Fase propietaria:** F08 — CMS Schema, Content Store, Workflow e Indexer

## Por qué existe
Esta microfase existe para **Content Type y Field Registry** dentro de la responsabilidad de `F08`: modelar CMS/workflow/indexes sin DDL dinámico. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Content Type y Field Registry** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

## Engine owner
`PGlite generic content store`

### Regla
Antes de escribir código, consulta la API pública del engine. Si ya existe la capacidad, úsala. ElectroCMS solo debe aportar canonical mapping, configuración, UX, adapter, target semantics o exportación.

## Packages/área de código
`data-core + content`

## Ubicación visual
Administrar > Modelos/Taxonomías/Relaciones/Contenido.


## Precondiciones
- Gate de entrada de `F08` satisfecho.
- Engine owner disponible detrás de su adapter.
- No existen errores P0/P1 de la dependencia inmediata.
- Tests existentes están verdes antes de modificar comportamiento.

## Implementación línea por línea
1. Construye `Administrar > Modelos` sobre ElectroSchema.
2. ContentType identity incluye: `id`, slug, singularName, pluralName, description, icon, public/private/internal, singleton, supports, admin menu visibility/order y capability policy refs.
3. ContentType template refs incluyen Single/Archive cuando el tipo sea routable; private/internal types pueden no exponer rutas.
4. Añade `storageHint`: `generic` default o `dedicated-target`.
5. `storageHint=dedicated-target` NO crea una tabla dinámica en el Studio/Native; solo informa exporters LAMP/WordPress de una optimización target-native soportada.
6. FieldRegistry define: type, label/key, description/help, default, placeholder, required, validation, options, conditional visibility, role visibility/editability, grouping/tab metadata y flags searchable/filterable/sortable/faceted.
7. Tipos mínimos: text, textarea, richtext, number, currency, email, phone, URL, date/time/datetime, color, select, radio, checkbox, switch, image, gallery, file, map, relation, user, taxonomy, group, repeater, calculated, conditional.
8. Model Builder Fields usa filas compactas expandibles; opciones técnicas raras van en Advanced mediante Progressive Disclosure.
9. Field changes actualizan metadata/index rebuild needs; jamás physical DDL en Studio.
10. Eliminar/renombrar field muestra usage/data impact y requiere migration/data-retention strategy explícita.
11. Test public/private/internal/singleton, menu order, templates, all field families, storageHint and schema round-trip.
