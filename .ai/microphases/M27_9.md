# M27.9 — Cerrar Professional Capability Coverage Matrix

**Fase propietaria:** F27 — Cross-Target QA, Editable Store Fixture y Release

## Por qué existe
Verificar que la racionalización OSS no haya eliminado capacidades del Prompt Maestro.

## Resultado exacto
Al cerrar esta microfase, **Cerrar Professional Capability Coverage Matrix** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`cross-target fixture/test harness`

## Responsabilidad ElectroCMS
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
QA fixtures/release reports; no nueva product UI salvo diagnostics.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Compara Prompt Maestro, TRACEABILITY, PROFESSIONAL_CAPABILITY_MATRIX, phase owners, code/tests y export reports.
2. Busca requisitos sin owner, duplicados, contradicciones y funciones marcadas complete sin evidencia.
3. Verifica workflow/revisions, flexible fields/options/profiles, query merge/cache/facets, form calc/frontend edit, quick edit/bulk/saved views, automation/audit.
4. Verifica 20 blueprints, role presets, media features, themes/templates, breakpoints y editor advanced.
5. Verifica Local/React/Native/LAMP/WordPress mappings y `professionalStudio` manifest.
6. Reabre la microfase propietaria de cualquier gap; no añadas una nueva subsystem phase por reflejo.
7. Zero P0/P1 ownership gaps antes de release.
8. Firma FINAL_COVERAGE_REPORT con evidence links.

## Artefactos obligatorios al cerrar
- `FINAL_COVERAGE_REPORT.md`
- `requirements ownership check`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Tests obligatorios

2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.
