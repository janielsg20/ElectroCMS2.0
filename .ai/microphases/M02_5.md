# M02.5 — Definir Theme, Blueprint, Registries y Capability ownership

**Fase propietaria:** F02 — Modelo canónico mínimo, ownership y versionado

## Por qué existe
Esta microfase existe para **Definir Theme, Blueprint, Registries y Capability ownership** dentro de la responsabilidad de `F02`: definir ownership/modelos portables mínimos. Debe cerrar una capacidad concreta y no abrir un subsystem paralelo.

## Resultado exacto
Al cerrar esta microfase, **Definir Theme, Blueprint, Registries y Capability ownership** debe existir como capacidad real, integrada y verificable. No se acepta placeholder ni una implementación paralela al engine.

`Zod boundaries`

### Regla

## Precondiciones
- `M02.4` COMPLETADA.
- Engine owner disponible detrás de su adapter.
- No existen errores P0/P1 de la dependencia inmediata.
- Tests existentes están verdes antes de modificar comportamiento.

## Implementación línea por línea
1. Define `ElectroTheme` exclusivamente para diseño visual: tokens, typography, variants, spacing, radius, shadows y motion.
2. NO definas un `ElectroTemplate` con un segundo árbol visual: un template es `ElectroDocument.kind="template"` + `templateMeta` + Display Conditions.
3. Define `ElectroBlueprintPackage` como paquete instalable externo; un proyecto solo guarda `originBlueprint` opcional y el resultado instalado como objetos normales.
4. Define `ElectroPlatformCapabilityRegistry` como registry versionado de la aplicación, no como un objeto completo serializado dentro de cada proyecto.
5. El proyecto guarda/deriva solo `requiredCapabilities` y target-specific overrides cuando sean necesarios.
6. Define Component/Field/Action/Provider registries como app registries; solo definitions creadas por el usuario se persisten dentro del proyecto.
7. Documenta ownership en `MODEL_OWNERSHIP.md`.
