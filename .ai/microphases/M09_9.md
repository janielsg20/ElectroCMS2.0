# M09.9 — Añadir consultas multifuente y Merge/Union portable

**Fase propietaria:** F09 — Bindings, Queries, Listings, Facets y Runtime Cache

## Por qué existe
Recuperar la capacidad profesional de consultas multifuente sin convertir Query Builder en SQL IDE.

## Resultado exacto
Al cerrar esta microfase, **Añadir consultas multifuente y Merge/Union portable** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`React Query Builder + TanStack Query + PGlite query adapter`

## Responsabilidad ElectroCMS
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
Administrar > Consultas, Filter UI e Inspector > Data.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. ElectroQueryDefinition permite `sources[]` con type ContentType, SavedQuery, Relation o Provider.
2. Define `combineMode`: single, merge o union; no soportes join arbitrario cross-provider sin adapter explícito.
3. Cada source declara output schema/type shape para validar compatibility.
4. RQB rules se aplican por source o a una normalized layer según configuración documentada.
5. Merge ordena/combina resultados en runtime only when result shapes compatible; Union dedup strategy explícita.
6. Pagination total/cursors de múltiples providers puede ser unsupported; Compatibility/Query diagnostic debe explicarlo.
7. Cache key incluye source versions.
8. Prueba merge de dos Content Types compatibles y rechazo de shapes incompatibles.

## Artefactos obligatorios al cerrar
- `MultiSourceQueryDefinition`
- `QueryCombineAdapter`
- `multisource tests`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.
