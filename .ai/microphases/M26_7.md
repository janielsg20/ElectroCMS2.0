# M26.7 — Auditar APIs experimentales y fijar dependency baseline

**Fase propietaria:** F26 — Hardening, Deploy Boundaries y Post-Core Guardrails

## Por qué existe
Evitar que el core dependa inadvertidamente de APIs alpha/experimental de los engines OSS.

## Resultado exacto
Al cerrar esta microfase, **Auditar APIs experimentales y fijar dependency baseline** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`toolchain audits/security/a11y/performance`

## Responsabilidad ElectroCMS
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
Settings/quality reports/Deploy boundaries.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Revisa release notes/docs oficiales de Puck, Refine, Rete, RQB, PGlite, Drizzle, Expo/Router, Zustand, Tiptap y NativeWind.
2. Genera `DEPENDENCY_BASELINE.md` con versión probada, licencia, APIs críticas usadas y stability status.
3. Marca Puck overrides/plugins experimentales, Expo Native Tabs u otras APIs alpha; ninguna puede ser release-critical sin fallback.
4. Revalida Puck AI: debe permanecer optional/post-core mientras requiera cloud/account/API key y no cumpla local-first core.
5. Ejecuta dependency audit/licensing and build fixtures después de pinning.
6. No copies exact version from old docs without rechecking package release compatibility.
7. Define upgrade cadence and adapter contract tests.
8. Block release if a critical path depends exclusively on an unstable API.

## Artefactos obligatorios al cerrar
- `DEPENDENCY_BASELINE.md`
- `OSS stability audit`
- `license manifest`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Tests obligatorios
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.
7. lint.
8. typecheck.
9. test.
10. build.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.

## Evidencia TRACKING
- archivos modificados;
- engine/API usado;
- pruebas ejecutadas;
- build/fixture;
- blockers/adaptations;
- siguiente microfase.
