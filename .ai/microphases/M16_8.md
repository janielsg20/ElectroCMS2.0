# M16.8 — Racionalizar Project Kit: Theme + Templates + Blueprint

**Fase propietaria:** F16 — Blueprint Engine, Project Kits y Professional Capability Packs

## Por qué existe
Conservar la experiencia de importar un paquete completo sin sobrecargar el concepto Theme.

## Resultado exacto
Al cerrar esta microfase, **Racionalizar Project Kit: Theme + Templates + Blueprint** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`BlueprintInstaller + existing core engines`

## Responsabilidad ElectroCMS
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
New Project Wizard / Project Kits catalog.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Define UI `Project Kit` como paquete compuesto opcional de Theme + Template Pack + Blueprint content/schema/admin config.
2. Theme permanece visual-only.
3. Template Pack permanece visual document-only.
4. Blueprint permanece full project configuration.
5. Project Kit installer permite `Design only`, `Templates`, `Structure`, `Demo data` selective install.
6. Conflicts se resuelven por cada subpackage antes de commit.
7. La UI puede presentar un Kit como una unidad, pero storage mantiene ownership separado.
8. Esto reemplaza la vieja idea de Theme conteniendo CPTs/roles/demo data sin perder funcionalidad.
9. Prueba aplicar Design only sin tocar content.

## Artefactos obligatorios al cerrar
- `PROJECT_KIT_SPEC.md`
- `ProjectKitInstaller composition tests`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Tests obligatorios
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.
6. Target fixture si afecta export/native/server.
7. lint.
8. typecheck.
9. test.
10. build.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.
