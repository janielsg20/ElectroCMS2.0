# M08.8 — Modelar Global Options, Profiles y Data Stores sin nuevos engines

**Fase propietaria:** F08 — CMS Schema, Content Store, Workflow e Indexer

## Por qué existe
Preservar equivalentes a option pages/profiles/data stores reutilizando Content Types y permisos.

## Resultado exacto
Al cerrar esta microfase, **Modelar Global Options, Profiles y Data Stores sin nuevos engines** debe quedar integrado, persistido/exportable cuando corresponda y cubierto por pruebas. No basta con un tipo, un botón o un placeholder.

## Engine owner
`PGlite/Drizzle + ElectroSchema`

## Responsabilidad ElectroCMS
Construye únicamente la semántica portable, adapter, configuración, UX y diagnostics que el engine no trae. No dupliques el motor.

## Ubicación visual
Administrar > Modelos/Contenido/Taxonomías/Relaciones.

## Precondiciones
- La microfase anterior de la fase está COMPLETADA o la dependencia está documentada como ya disponible.
- Los contratos canónicos necesarios existen.
- El engine owner está encapsulado detrás del adapter correspondiente.

## Implementación línea por línea
1. Implementa `singleton`/`internal` flags en ContentType metadata.
2. Global Options = ContentType singleton con un único record y sin archive público.
3. User Profile = ContentType/field group linked one-to-one to userId o relation user; no nuevo profile database engine.
4. Internal Data Store = private ContentType/list con admin visibility configurable.
5. Flexible Content se expresa mediante Group/Repeater/block-like field structures existentes.
6. Todos usan RecordService, FieldRegistry, permissions, Query/Binding y exporters existentes.
7. UI Model Builder ofrece presets `Global Options`, `User Profile`, `Internal Data Store` que crean configuración normal, no special-case hardcode.
8. Prueba export mapping a React/LAMP/WordPress strategy.

## Artefactos obligatorios al cerrar
- `content-type presets`
- `singleton validation`
- `profile/data-store tests`

## Estados y errores
- Define empty/loading/error/disabled/blocked cuando tengan sentido.
- Un caso unsupported nunca se convierte silenciosamente en success.
- Diagnostics deben incluir código, ubicación, causa y acción sugerida.

## Responsive y accesibilidad si toca UI
- Desktop high-density sin overflow.
- Tablet usa Sheet/Drawer para tooling secundario.
- Mobile usa route/card/bottom-sheet, no desktop comprimido.
- Keyboard/focus-visible/aria-label.
- Alternative a DnD/gestos.

## Tests obligatorios
1. Unit/contract del valor Electro.
2. Integration con engine/storage real.
3. Negative/failure path.
4. Round-trip si persiste canonical data.
5. E2E si existe UI.

## Prohibido
- No crear subsystem paralelo.
- No persistir engine internals como modelo canónico.
- No usar mocks permanentes.
